# 决策单选项 1 的唯一前置：**已确认成立**——数据商有这段历史，是缓存用错了 API（2026-09-15 04:35）

决策单 v0.1 §5 写着："没有验证'数据商能否提供 2023-09-25 之前的科创板行业成员'——**这是选项 1 的唯一前置，
尚未确认**"。本文把这一条测完了，结论是**能**，而且顺带推翻了两处已有说法。

**一句话**：数据商有**两支**行业成员 API。在用的缓存是 `index_member(index_code=…)` 建的，
这支 API 把**每一只科创板股票的 `in_date` 都钉死在 2023-09-25**；另一支 `index_member_all` 给的是
真实入指日期，**最早 2019-06-26**，而且是在用缓存的**严格超集**（多 9 只、少 0 只）。
所以那 21 个月的板块级空洞**不是数据商没有数据，是我们问错了接口**。

所有数字都由 `probes/` 下四个脚本生成，机读件在 `measurements/option1_*.json`，
数据商原始应答的字节副本在 `vendored_member_all/`（含 `MANIFEST.json` 与 `combined_sha256`）。
**没有一个数字是手抄的。**

---

## 1. 两支 API 的差别，逐条对齐

| | 在用的缓存 | 另一支 API |
|---|---|---|
| 调用 | `pro.index_member(index_code=…)` | `pro.index_member_all(l1_code=…, is_new∈{Y,N})` |
| 文件 / 行数 | 31 个文件，**7,733** 行 | 一次抓取，**7,912** 行 |
| 科创板行数 / 只数 | 624 行 / **612** 只 | 718 行 / **621** 只 |
| **科创板最早 `in_date`** | **2023-09-25** | **2019-06-26** |
| 全表最早 `in_date` | 1990-12-10 | 1984-05-09 |
| 独有代码 | **0 只** | **9 只**：`688086 688555 688801 688826 688828 688835 688836 688837 689009` |

`689009.SH`（九号公司-WD）就是 `root_cause.md` 里"缓存里完全不存在"的那只——
`index_member_all` 有它：`801880.SI 汽车，in_date 20201029`，即上市当日。**不是缺数据，是缺接口。**

两只样本的逐条对照（机读件 `measurements/option1_vendor_api_feasibility.json`）：

```
688003.SH  缓存      : 801890.SI            in_date 20230925  out_date —        is_new Y
           member_all: 801890.SI 机械设备    in_date 20190626  out_date 20210729  is_new N
                       801890.SI 机械设备    in_date 20210730  out_date —        is_new Y

688002.SH  缓存      : 801740.SI            in_date 20230925  out_date —        is_new Y
           member_all: 801740.SI 国防军工    in_date 20190626  out_date 20260820  is_new N
                       801080.SI 电子        in_date 20260821  out_date —        is_new Y
```

`688003.SH` 两条记录 **L1 相同**，唯一丢的是 4 年的 `in_date`。
`688002.SH` 更值得注意：缓存是 2026-08-14 建的，那天 `801740` **确实还是现行行业**；
换成 `801080 电子` 发生在 **2026-08-21**，即建缓存**之后一周**。
所以 `vendored_industry_cache/MANIFEST.json` 里"数据商重述过这段历史"的说法**不成立**——
那是一次**缓存建好之后才发生的真实调行业**，加上一个**系统性的 `in_date` 截断**，两件事被误读成了一件。

## 2. 机制被精确证明：这些行**只**缺 357 与 471，别的什么都不缺

`probes/probe_star_rows_in_denominator.py` 直接读评估器自己的两张表
（`dfs://QuantResearchV2Test` 的 `label_daily` / `factor_daily`，**只读**，按年解析 `data_version`，
与仪器同一套解析规则），先做了一件必须做的事：**逐日复现仪器**。

> 分子 24/24 逐日相同，分母 24/24 逐日相同（`reproduces_the_instrument.verdict = "EXACT"`）。
> 复现不过就不允许往下分解——这是这个探针的前置断言，不是事后说明。

复现通过之后，把每天的有效标签行按"是不是科创板"拆开：

| 量 | 24 天的取值 |
|---|---|
| 科创板有效标签行 | **181 – 330** |
| 其中已集齐九因子的 | **0**（24 天全是 0） |
| 科创板行里 `yeslab_357` 命中数 | **0**（24 天全是 0） |
| 科创板行里 `yeslab_471` 命中数 | **0**（24 天全是 0） |
| 科创板行里**其余 7 个**因子命中率 | **0.9936 – 1.0031** |
| 到达 0.90 地板还差几行 | **1 – 36** |
| 可修行数（= 科创板行 − 已集齐） | **181 – 330** |
| **余量（可修 − 还差）** | **最小 164** |
| 剩余的非科创板缺口 | 28 – 171 行 |

**科创板行不多不少正好缺那两个行业因子，其余七个几乎全有。** 这不是"覆盖率偏低"，
这是一个开关：行业标签在 → 357/471 在 → 该行进入交集。
（命中率偶尔 >1 是因为 `factor_daily` 里有少量科创板行不在当日 `label_valid` 集合内，
即分子分母的口径差，已按仪器的规则把分子限制在有效标签行内。）

对照决策单 v0.1 里被否掉的那个伪选项："只移 `yeslab_206`" 救回 21 天但**余量只有 0–8 行**，
所以判定为巧合。这里的余量是 **164 – 329 行**，量级差 20 倍以上，性质不同。

## 3. 选项 1 的价格：从"未知"变成一个数

`probes/project_option1.py` 用上下两界定价（逐日明细 `measurements/option1_price.json`）：

* **乐观界**：所有尚未集齐的科创板行都变完整；
* **保守界**：只有已经带着其余七个因子的科创板行才变完整（逐日取七个因子里最小的命中数）。

| | 乐观 | 保守 |
|---|---|---|
| 补齐后跌破地板的天数 | **0**（原 24） | **0**（原 24） |
| **G6** | **1.000000** | **1.000000** |
| 最差日 | 2022-07-29 | 2022-07-29 |
| **最差日覆盖率** | **0.949031** | **0.949031** |
| 高于 0.90 地板 | +0.049031 | +0.049031 |
| **达到 §4.1 提议的 0.95 门槛？** | **否，差 4 行** | **否，差 4 行** |

两界在最差日**重合**（2022-07-29 那天 181 行科创板行七个因子全有），所以这个数是可用的。
其余 945 天只会更好——补齐只加行、不减行。

**这是决策单 v0.1 没有的数**：v0.1 把选项 1 的稳健性写成"与选项 2 同一量级（见下）"。
实测**不是**同一量级——选项 2 的 `coverage_min` 是 **0.971370**，选项 1 是 **0.949031**，
低 **0.0223**。而且按 v0.1 §4.1 自己提的验收标准（"全年最低逐日交集覆盖率 ≥ 0.95"），
**选项 1 不达标，差 4 行**；差在 2022-07-29，即数据商每年 6 月底/7 月初批量到期的那一天（§10.3 普查）。
选项 2 达标。

所以真实的取舍是：**选项 1 保住九因子的对照强度、但稳健性差 4 行不到 0.95；
选项 2 稳健性够、但 G4 会被抬高**（B0–B3 全按稠密集构造）。v0.1 把它们并列成"都到 1.000000"，
掩盖了这个差别。

## 4. 重述风险 ≈ 0：补齐是**加法**，不会改动已发布的因子值

选项 1 最大的隐忧是：补历史会不会顺手把**已经烘进已发布因子**的标签改掉？
在两支 API **都有**科创板标签的重叠窗口上直接量（`2023-09-25 … 2025-12-31`，每第 10 个交易日取一天）：

| 量 | 值 |
|---|---|
| 比较的（证券, 日）对 | **34,571** |
| L1 标签完全相同 | **34,570** |
| **一致率** | **0.999971** |
| `member_all` 里同日有多个现行 L1 的行 | **0** |

唯一一处不一致（`measurements/option1_overlap_disagreements.json`）：

```
2024-05-20  688292.SH   缓存 801770.SI(通信)   member_all 801750.SI(计算机)
```

**一处，34,571 分之一。** 也就是说：换成 `index_member_all` 重建缓存，
对 2023-09-25 之后已经发布的值**几乎不产生任何改动**，改动集中在**新增** 2019-07…2023-09 那段。
这大幅降低了选项 1 的谱系代价——它更像"补一段缺失的历史"，而不是"重述已有的历史"。

## 5. 更正：所谓"两支行业缓存互相印证"是**同一份数据**

`probe_industry_label_census.py` 的 `SOURCES` 把 `pit_industry_sw2014_members_*` 与
`pit_industry_members_*` 当作 SW2014 / SW2021 两半分别汇报，读起来像一次交叉验证。
`probes/probe_cache_halves_not_independent.py` 逐文件哈希后：

* 两半重叠的 **27 个行业文件，27 个字节级完全相同**（一致率 **1.0000**）；
* 两半的科创板最早 `in_date` **同为 20230925**；
* **`pit_industry_sw2021_members_*` 一个文件都不存在**——`fetch_pit_members` 对 SW2021 走的是
  遗留文件名回退分支，所以"SW2021 那一半"**就是**遗留那一半；
* 原因在构建代码本身：`research_v2/scripts/audit_tushare_pit_industry.py:472` 调
  `pro.index_member(index_code=…)`，**这支 API 不接受 `src` 参数**，
  于是同一个 `index_code` 无论你自以为在查哪套分类，返回的都是同一批行。
  真正随 `src` 变的只有 `index_classify` 拿到的**分类表**（28 vs 31 个 L1 代码），成员表不变。

**结论**：`root_cause.md` 与 `dense_intersection_screen/finding.md` §10.3 里
"两支行业缓存都给出 2023-09-25"这类表述，**不构成两次独立观测**。
根因结论本身不受影响（本文第 1、2 节用两支**不同**的 API 与评估器自己的表独立复核过），
但"互相印证"这个措辞必须撤回。

## 6. 本文没有做的事

* **没有改任何代码、缓存、门值、地板、冻结集、签名工件或数据库。**
  `research_v2/artifacts/tushare_cache/` 一个字节都没动；数据库只做了 SELECT。
* **没有重放上游管线**。第 2 节证明的是"标签供给"这一必要条件与充分性算术：
  357/471 由上游按行业标签生成，本文量的是标签能不能供上、以及供上之后行数够不够过地板，
  **不是**一次真实的因子重放。选项 1 若被批准，"补上行业历史后重放能否复现 YesLab 的存量值"
  仍是**下一步的前置工作**（v0.1 §5 最后一条依然未做）。
* **没有替所有者选选项**。第 3 节只是把选项 1 的价格从"未知"改成一个数，并指出它不满足
  v0.1 §4.1 自己提的 0.95 门槛。
* 没有测 `index_member_all` 的 L2/L3 层级；本文只用 L1，因为 357/471 的依赖是 L1 行业标签。

## 7. 复现

```bash
cd <evidence>/star_industry_coverage
# 1) 抓数据商另一支 API（约 60 秒，只读，结果已 vendored）
python probes/fetch_member_all.py --out-dir /tmp/opt1_raw
# 2) 前置：另一支 API 有没有 2023-09-25 之前的科创板成员
python probes/analyze_backfill_feasibility.py --raw /tmp/opt1_raw \
       --out measurements/option1_vendor_api_feasibility.json
# 3) 精确分解：24 天里缺的行有多少是科创板行（读评估器的两张表，SELECT-only）
python probes/probe_star_rows_in_denominator.py --days <24 天清单> \
       --out measurements/option1_star_rows_in_denominator.json
# 4) 定价：补齐后地板会看到什么
python probes/project_option1.py --rows measurements/option1_star_rows_in_denominator.json \
       --out measurements/option1_price.json
# 5) 更正：两支缓存是不是同一份数据
python probes/probe_cache_halves_not_independent.py \
       --out measurements/cache_halves_not_independent.json
```
