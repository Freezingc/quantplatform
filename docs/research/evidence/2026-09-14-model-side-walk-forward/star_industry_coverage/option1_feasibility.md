# 决策单选项 1 的唯一前置：**已确认成立**——数据商有这段历史，是缓存用错了 API（2026-09-15 04:35）

决策单 v0.1 §5 写着："没有验证'数据商能否提供 2023-09-25 之前的科创板行业成员'——**这是选项 1 的唯一前置，
尚未确认**"。本文把这一条测完了，结论是**能**，而且顺带推翻了两处已有说法。

**一句话**：数据商有**两支**行业成员 API。在用的缓存是 `index_member(index_code=…)` 建的，
这支 API 把**每一只科创板股票的 `in_date` 都钉死在 2023-09-25**；另一支 `index_member_all` 给的是
真实入指日期，**最早 2019-06-26**，而且是在用缓存的**严格超集**（多 9 只、少 0 只）。
所以那 21 个月的板块级空洞**不是数据商没有数据，是我们问错了接口**。

所有数字都由 `probes/` 下四个脚本生成，机读件在 `measurements/option1_*.json`，
数据商原始应答的字节副本在 `vendored_member_all/`（含 `MANIFEST.json` 与 `combined_sha256`）。
**没有一个数字是手抄的。**

## 1. 两支 API 的差别，逐条对齐

| | 在用的缓存 | 另一支 API |
|---|---|---|
| 调用 | `pro.index_member(index_code=…)` | `pro.index_member_all(l1_code=…, is_new∈{Y,N})` |
| 文件 / 行数 | 31 个文件，**7,733** 行 | 一次抓取，**7,912** 行 |
| 科创板行数 / 只数 | 624 行 / **612** 只 | 718 行 / **621** 只 |
| **科创板最早 `in_date`** | **2023-09-25** | **2019-06-26** |
| 全表最早 `in_date` | 1990-12-10 | 1984-05-09 |
| 独有代码 | **0 只** | **9 只**：`688086 688555 688801 688826 688828 688835 688836 688837 689009` |

`689009.SH`（九号公司-WD）就是 `root_cause.md` 里"缓存里完全不存在"的那只——
`index_member_all` 有它：`801880.SI 汽车，in_date 20201029`，即上市当日。**不是缺数据，是缺接口。**

两只样本的逐条对照（机读件 `measurements/option1_vendor_api_feasibility.json`）：

```
688003.SH  缓存      : 801890.SI            in_date 20230925  out_date —        is_new Y
           member_all: 801890.SI 机械设备    in_date 20190626  out_date 20210729  is_new N
                       801890.SI 机械设备    in_date 20210730  out_date —        is_new Y

688002.SH  缓存      : 801740.SI            in_date 20230925  out_date —        is_new Y
           member_all: 801740.SI 国防军工    in_date 20190626  out_date 20260820  is_new N
                       801080.SI 电子        in_date 20260821  out_date —        is_new Y
```

`688003.SH` 两条记录 **L1 相同**，唯一丢的是 4 年的 `in_date`。
`688002.SH` 更值得注意：缓存是 2026-08-14 建的，那天 `801740` **确实还是现行行业**；
换成 `801080 电子` 发生在 **2026-08-21**，即建缓存**之后一周**。
所以 `vendored_industry_cache/MANIFEST.json` 里"数据商重述过这段历史"的说法**不成立**——
那是一次**缓存建好之后才发生的真实调行业**，加上一个**系统性的 `in_date` 截断**，两件事被误读成了一件。

## 2. 机制被精确证明：这些行**只**缺 357 与 471，别的什么都不缺

`probes/probe_star_rows_in_denominator.py` 直接读评估器自己的两张表
（`dfs://QuantResearchV2Test` 的 `label_daily` / `factor_daily`，**只读**，按年解析 `data_version`，
与仪器同一套解析规则），先做了一件必须做的事：**逐日复现仪器**。

> 分子 24/24 逐日相同，分母 24/24 逐日相同（`reproduces_the_instrument.verdict = "EXACT"`）。
> 复现不过就不允许往下分解——这是这个探针的前置断言，不是事后说明。

复现通过之后，把每天的有效标签行按"是不是科创板"拆开：

| 量 | 24 天的取值 |
|---|---|
| 科创板有效标签行 | **181 – 330** |
| 其中已集齐九因子的 | **0**（24 天全是 0） |
| 科创板行里 `yeslab_357` 命中数 | **0**（24 天全是 0） |
| 科创板行里 `yeslab_471` 命中数 | **0**（24 天全是 0） |
| 科创板行里**其余 7 个**因子命中率 | **0.9936 – 1.0031** |
| 到达 0.90 地板还差几行 | **1 – 36** |
| 可修行数（= 科创板行 − 已集齐） | **181 – 330** |
| **余量（可修 − 还差）** | **最小 164** |
| 剩余的非科创板缺口 | 28 – 171 行 |

**科创板行不多不少正好缺那两个行业因子，其余七个几乎全有。** 这不是"覆盖率偏低"，
这是一个开关：行业标签在 → 357/471 在 → 该行进入交集。
（命中率偶尔 >1 是因为 `factor_daily` 里有少量科创板行不在当日 `label_valid` 集合内，
即分子分母的口径差，已按仪器的规则把分子限制在有效标签行内。）

对照决策单 v0.1 里被否掉的那个伪选项："只移 `yeslab_206`" 救回 21 天但**余量只有 0–8 行**，
所以判定为巧合。这里的余量是 **164 – 329 行**，量级差 20 倍以上，性质不同。

掩盖了这个差别。

## 4. 重述风险 ≈ 0：补齐是**加法**，不会改动已发布的因子值

> **【更正，同日 06:35】本节的 0.999971 是在**科创板子集**上量的，不能当作全样本结论。已撤回。**
> 全样本口径下（§14）：13,010,933 个"两支都有标签"的证券日里，**一致率是 0.947265**，
> **真正判不同行业的有 462,588 个证券日（3.555%）、平均每天 136.4 个证券**，分布在 2,208 天上。
> 所以"换 API 对已发布的值几乎无改动"**只在科创板成立**；
> 在全样本上，选项 1 会**改变**约每天 136 个证券的 L1 标签，从而改变它们的 `357`/`471` 取值。
> **这不影响 §2/§3/§8 的任何覆盖率与 G6 结论**（那些只取决于标签**有没有**，不取决于**是哪个**），
> 但它确实推翻了"改动是纯加法"这个说法：选项 1 在**行的存在性**上是加法，
> 在**标签取值**上不是。谱系代价要按后者写。

选项 1 最大的隐忧是：补历史会不会顺手把**已经烘进已发布因子**的标签改掉？
在两支 API **都有**科创板标签的重叠窗口上直接量（`2023-09-25 … 2025-12-31`，每第 10 个交易日取一天）：

| 量 | 值 |
|---|---|
| 比较的（证券, 日）对 | **34,571** |
| L1 标签完全相同 | **34,570** |
| **一致率** | **0.999971** |
| `member_all` 里同日有多个现行 L1 的行 | **0** |

唯一一处不一致（`measurements/option1_overlap_disagreements.json`）：

```
2024-05-20  688292.SH   缓存 801770.SI(通信)   member_all 801750.SI(计算机)
```

**一处，34,571 分之一。** 也就是说：换成 `index_member_all` 重建缓存，
对 2023-09-25 之后已经发布的值**几乎不产生任何改动**，改动集中在**新增** 2019-07…2023-09 那段。
这大幅降低了选项 1 的谱系代价——它更像"补一段缺失的历史"，而不是"重述已有的历史"。

## 5. 更正：所谓"两支行业缓存互相印证"是**同一份数据**

`probe_industry_label_census.py` 的 `SOURCES` 把 `pit_industry_sw2014_members_*` 与
`pit_industry_members_*` 当作 SW2014 / SW2021 两半分别汇报，读起来像一次交叉验证。
`probes/probe_cache_halves_not_independent.py` 逐文件哈希后：

* 两半重叠的 **27 个行业文件，27 个字节级完全相同**（一致率 **1.0000**）；
* 两半的科创板最早 `in_date` **同为 20230925**；
* **`pit_industry_sw2021_members_*` 一个文件都不存在**——`fetch_pit_members` 对 SW2021 走的是
  遗留文件名回退分支，所以"SW2021 那一半"**就是**遗留那一半；
* 原因在构建代码本身：`research_v2/scripts/audit_tushare_pit_industry.py:472` 调
  `pro.index_member(index_code=…)`，**这支 API 不接受 `src` 参数**，
  于是同一个 `index_code` 无论你自以为在查哪套分类，返回的都是同一批行。
  真正随 `src` 变的只有 `index_classify` 拿到的**分类表**（28 vs 31 个 L1 代码），成员表不变。

**结论**：`root_cause.md` 与 `dense_intersection_screen/finding.md` §10.3 里
"两支行业缓存都给出 2023-09-25"这类表述，**不构成两次独立观测**。
根因结论本身不受影响（本文第 1、2 节用两支**不同**的 API 与评估器自己的表独立复核过），
但"互相印证"这个措辞必须撤回。

## 9. 选项 1 有两种实现，安全性差一个量级：**并集**，不是替换

换 API **不是纯加法**。两支 API 把每年的成分调整空洞放在**不同的日子**：

| | 缓存（`index_member`） | `index_member_all` |
|---|---|---|
| 2022 年到期日 | **2022-07-29**，143 条到期 | **2022-07-28**，243 条到期 |
| 2023 年 | 2023-07-05 附近 | **2023-07-03**，74 条到期 |
| 2024 年 | 2024-07-30，68 条 | **2024-07-29**，117 条 |
| 2022-07-28 的 245 个失标证券与 2022-07-29 的失标证券**重合** | **5 个，重合率 0.020** | |

于是两种实现的差别（`measurements/option1_union_vs_replace.json`；
科创板收益在 **422/969** 天上是实测的——50 天逐证券 + 372 个盘前日按前缀聚合，
聚合口径的分母与仪器 **420/420** 全同；其余 547 天保守取 0）：

| | 跌破天数 | **G6** | 最差日覆盖率 | 距地板 0.01 以内的天数 |
|---|---|---|---|---|
| 现状 | 24 | 0.975232 | 0.890267 | — |
| **并集**（缓存 ∪ `index_member_all`） | **0** | **1.000000** | **0.949031**（只算科创板的保守值；§8 的全口径是 0.976751） | **0** |
| **替换**（只用 `index_member_all`） | **0** | **1.000000** | **0.903697** | **1**（2022-07-28，余量 **12.4 行**） |

**替换也会让 G6 = 1.000000，但它把 2022-07-28 压到只剩 12.4 行余量**——
与决策单已经否掉的"只移 `yeslab_206`"（余量 0–8 行）**同一类**。
**并集按构造是纯加法（失标证券恒为 0），所以选并集。**

> 这里也要更正我自己一次：这一节的第一版把替换算成"19 天跌破、124 天在 0.01 以内"，
> 那是因为对未逐日实测的天一律假设科创板收益为 0。把 420 个盘前日的科创板行数**实测**进来之后，

## 13. 并集的优先级规则：**三个候选都量了，推荐"优先 `index_member_all` + 沿用 provider 自己的决胜键"**

§9 说"选项 1 = 并集"，但决策单同时标了一条未实现未验证的前提：**并集需要一条显式优先级规则**，
因为两支 API 会给出不同标签。`probes/probe_union_precedence_rule.py` 把三个候选规则在
**2014-01-01…2026-12-31 全部 3,392 个工作日**上按 8 条性质逐条测（机读件
`measurements/union_precedence_{member_all,cache,surgical}.json`）：

* **`member_all`**：`index_member_all` 有标签就用它，否则用缓存；
* **`cache`**：缓存有标签就用它，否则用 `index_member_all`（= 纯加法，但保留缓存的一切毛病）；
* **`surgical`**：缓存为权威，`index_member_all` **只**补"cutover 之前的科创板"（能修那 24 天的最小改动）。

| 性质 | `member_all` | `cache` | `surgical` |
|---|---|---|---|
| **P1 决定性**（无歧义证券日） | 剩 **5,392** | 剩 **228,942** | 剩 **228,942** |
| **P2 不低于缓存** | **PASS（0 天）** | **PASS（0 天）** | **PASS（0 天）** |
| P2b 不低于 `member_all` | PASS（0 天） | PASS（0 天） | 3,388 天（**设计如此**，见下注） |
| **P3 科创板 cutover 前** | **383–563** | 383–563 | 383–563 |
| **P3 2014-01-02 行业数 / 在册** | **31 / 2,537** | 30 / 2,537 | **19 / 1,577（未修）** |
| **P3 2021-12-10 空洞** | **无**（4,821→4,825） | **无** | **仍在**（4,555→4,181） |
| **P4 ±50 大幅变动日** | **3** | **3** | **18** |
| **P5 掩盖真实到期的代价** | **41,028 证券日 = 0.2828%**，单日最多 532 | 437,753 = **3.0171%**，单日最多 484 | **0** |
| **P6 靠回退取到的标签数** | **157,209** | 1,340,882 | 336,808 |

> **P2b 那一格不是缺陷。** `surgical` 有意**不**吸收 `member_all` 的非科创板补充，
> 所以"不低于 `member_all`"对它不是应当成立的性质；对它成立的性质是"不低于缓存"，**PASS**。
> 我第一版把 P2 定义成"不低于任一来源"，于是给 `surgical` 报了一个 3,388 天的 FAIL——
> **那是性质定义错了，不是规则错了**，已按规则意图拆开重算并写回三份机读件。

**推荐：`member_all` 优先，外加一条决胜规则。** 理由全部是上表里的数：

1. **它在每条可比的性质上都不劣、在五条上明显更优**：歧义少 **42 倍**（5,392 对 228,942）、
   掩盖代价少 **10.7 倍**（0.283% 对 3.017%）、2014-01-02 多修 1 个行业、
   大幅变动日 3 对 18（`surgical`）、回退依赖少 8.5 倍。
2. **`surgical` 唯一胜过它的地方是 P5 = 0**（完全不掩盖真实到期）与"不动任何已有标签"。
   如果所有者把"已发布值一个都不许变"当成硬约束，`surgical` 是唯一满足的选择，
   代价是 **2014 左端与 2021-12-10 空洞都不修**（§10 那两处收益全部放弃）。
3. **P1 三个规则全都不单独通过**，因为歧义来自**缓存自身**，不是来自并集。
   所以需要补一条决胜规则——而这一条**不用新发明**：`build_pit_snapshot`
   （`audit_tushare_pit_industry.py:101-103`）**已经有**一条，
   `sort_values(["con_code","in_date","index_code"]).drop_duplicates(keep="last")`，
   即**最晚 `in_date` 胜，再按最大 `index_code`**。**直接沿用即可**，
   这样规则与线上行为一致，也不会引入第二种口径。
   沿用后 P1 的残余 5,392 个证券日 = 全部并集标签的 **0.037%**，且由既有代码确定性解决。

## 14. 【更正 §4】全样本一致率是 **0.947265**，不是 0.999971

§4 那个 0.999971 是**科创板子集**上的数（34,571 对）。把口径换成**全样本**
（`probes/probe_union_precedence_rule.py` 的 P7，3,392 天逐日）：

| 类别 | 证券日数 | 占比 |
|---|---|---|

| 缓存歧义、其他形状 | 5,146 | 0.040% |

**真正的分歧平均每天 136.4 个证券，分布在 2,208 天上。** 所以：

  "**行的存在性上是加法；标签取值上每天约 136 个证券会变，全样本一致率 0.947265**"。

## 15. 一条独立发现：**在用的缓存自身有 22.9 万个歧义证券日，其中 27.87% 由一个任意键决定**

量 P1 时量到的，与那 24 天无关也成立。`probes/probe_cache_ambiguity_tiebreak.py`
（机读件 `measurements/cache_ambiguity_tiebreak.json`）：

| 量 | 值 |
|---|---|
| 缓存里"同一证券同日有多个现行 L1"的证券日 | **228,942** |
| 每日均值 / 单日最多 | **67.5** / **155** |
| 有歧义的天数 | **2,072 / 3,392** |
| 其中**科创板** | **0**（缓存里每只科创板只有一条记录） |
| **被 `in_date` 真正决出的** | **165,134（72.13%）** |
| **落到"最大 `index_code`"这个任意键的** | **63,808（27.87%）** |
| `index_member_all` 的歧义证券日（170 个采样日） | **0** |

三点值得写下来：

1. **这不是静默吞掉的缺陷。** `build_pit_snapshot` 明确检测并上报：
   冲突数写进 `snapshot.attrs["overlap_conflict_code_count"]`、冲突代码写进
   `attrs["overlap_conflict_codes"]`，然后用一条**确定性**规则收敛到一行。设计是对的。
2. **但决胜键正是 `in_date`，而 `in_date` 恰好是 `index_member` 对科创板伪造的那个字段。**
   科创板上这不构成问题（每只只有一条记录，歧义为 0），
   可在**非科创板**上，有 **27.87%** 的歧义因为候选记录 `in_date` 相同而**决不出来**，
   最终由"最大 `index_code`"选中——**那是一个没有业务含义的键**。
   也就是说：**当前管线里每天约有 19 个证券（63,808 ÷ 3,392）的行业标签是任意选出来的。**
3. **`index_member_all` 把这个问题整个消掉**（170 个采样日歧义恒为 0）。
   所以选项 1 的收益不止"补回 21 个月的科创板历史"，还包括
   "**把 27.87% 的任意选择换成唯一正确答案**"——这一条此前没有任何文档提过。
