### 决定 B（**新增，本清单里唯一会算错数的一项**）：跨报告期的基本面版本优先级

**实测缺陷**：`expand_fundamental_events` 的版本排序键是
`["available_date", "report_period", "source_revision_id"]` 全降序，**`available_date` 是第一键**。
构造 FY2024（`report_period` 2024-12-31，公告 2025-03-28，available 03-31）与
**对更旧 Q3 2024 的迟到重述**（公告 2025-04-10，available 04-11），在 signal date 2025-04-15：

```
signal_date report_period  raw_value  available_date  source_revision_id  stale_days
 2025-04-15    2024-09-30        1.5      2025-04-11    q3-2024-restated           4
```

**发布的是被重述的 Q3（1.5），FY2024（2.0）被丢弃**——报告期**向后退了一格**
（同一 fixture 在 2025-04-01 发布的是 FY2024，测试对此有显式断言）。
按通常 PIT 基本面语义这是错的：某日的值应来自**当时可得的最新报告期**，修订只在**同一期内**决胜。

**规格两可**：C4.3 把区间定义为到 `next_version_available_date - 1 trading day`
（**单一线性版本序列**，即现状）；C4.4 只讲**同一 report period 内部**的修订。**都没说跨期谁压谁。**

- **(B-i) 最新报告期优先，修订仅在同期内决胜**：排序键改为
  `report_period DESC, available_date DESC, source_revision_id DESC`。
  代价：C4.3 的区间公式须重述为**按报告期分组**，因为不同期的有效区间会**重叠**、不再线性。
- **(B-ii) 最新可用版本优先（现状）**：与 C4.3 字面一致。代价：如上，报告版本会因旧期重述而倒退。
- **(B-iii) 并列输出、由下游按因子语义决定**：代价：展开不再是每 (signal_date, ts_code) 一行，
  波及 C5 的统一 observation 输出契约。

**附带更正一条测试名的过度承诺**：既有测试
`test_fundamental_event_prefers_latest_report_period_before_revision` 的名字断言"报告期优先于修订"，
但其 fixture 给两个版本**同一 `ann_date`**，故 `available_date` 相同、排序落到第二键才正确。
**名字读起来像一条 precedence 保证，实际只是一条 tie-break 保证。**（测试本身是好的。）

### 决定 C（**被 B 阻塞**）：基本面展开的性能重写

**实测成本**：`expand_fundamental_events` 是**逐 universe 行的 Python 循环**，
每行对**整个 events 帧**做一次布尔掩码 → `O(universe_rows × events)`。
输出**不是**笛卡尔积（只为实际 universe 成员产出行），**但时间是**。

```
 universe  events   seconds    us/universe-row  rows out
      500     100      0.83             1664.4       190
     1000     200      1.29             1286.0       190
     2000     400      2.74             1371.1       380
     4000     400      6.71             1677.9      1350
     8000     800     13.99             1748.4      2339
```

外推（~1676 µs/行）：**单因子单折**（5000×250 = 1,250,000 行）≈ **0.6 h**；
**487 因子单折** ≈ **12 因子·天**；**6 折** ≈ **71 天**。
每行成本在 universe 规模 16 倍区间内持平到上升，**不是预热假象**。
证据：`/data/zhangyudong/qrv2_research_artifacts/fundamental_expansion_scaling.txt`。

**正解**（as-of/区间连接：按证券把版本按 `available_date` 排序，用 `merge_asof`/`searchsorted`，
`O((N+M) log M)`）**必须逐位复现现在的 tie-break 顺序**——而那正是决定 B 争议的东西。
**故：先定 B，再重写 C。先做 C 等于把有争议的规则固化进更快的路径，日后要改两处。**

### 决定 D：C7.4 代表因子排序键——以规格还是以实现为准

规格：`eligible → FDR pass → direction stability → median abs IC → coverage → lower conflict rate → factor_id ASC`

### 决定 E：C7.1 的 scope 绑定与 C7.2 的覆盖率分母（**两项须一并定**）

- **C7.1**：`compute_factor_similarity(observations, *, start_date, end_date, minimum_common_members,
  minimum_valid_days)` —— **没有 `universe_id`，没有 `data_version`，模块内无任何 query builder / SQL**。
  它接收调用方已装配好的内存长表，故 scope **只由日期界定**：
  **同一 universe 换个数据版本、或换个 universe 而日期相同，算出的相似度无从区分，也不会报错。**
  与 C7.3 已交付的 `cluster_id` 内容寻址形成对照——**簇有稳定身份，而产生它的相似度矩阵
  没有记录自己是在哪个 universe / 哪个数据版本上算的**，故跨折或跨版本比较簇时无法判断可比性。
  日期闭区间与 scope 隔离**已满足且有测试**。
- **C7.2**：四款中三款成立（同日共同非空 ≥30、有效日 `abs(rho)` 中位数、有效日 <60 标 INSUFFICIENT
  且不连边）；**缺"覆盖"字段**。`valid_days` 不能代替：两个 pair 可同为 `valid_days == 60`，
  一个每天在 4000 个标的上算、另一个每天刚好卡在 30 的下限，**当前输出无法区分这两种证据强度**，
  而下游正是拿这个中位数去连边、去选代表。
- **为何须一并定**：覆盖至少三种口径——(i) 有效日共同成员中位数 ÷ 该日 universe 全量；
  (ii) ÷ 两因子各自覆盖的并集；(iii) 有效天数 ÷ scope 内总交易日数（已被 `valid_days` 隐含）。
  **(i) 最贴近"证据强度"，但它需要 universe 口径输入——正是 C7.1 缺的那个绑定。**
  先挑一个分母写进去、事后再改，会改变 `INSUFFICIENT` 之外的**所有输出数值**，
  进而可能改变连边与代表选择。

### 决定 F：quarantine 证据列的 JSON 格式（**已实测为非法 JSON**）

发布层聚合 quarantine 时用 `json.dumps`，过滤条件是 `pd.notna`——**`pd.notna(inf)` 为 True**，
故 `distinct_values_json` 可以是 **`"[Infinity]"`**，**RFC 8259 不允许**，
严格解析器（数据库 JSON 函数、JS `JSON.parse`、serde_json）**直接拒绝**。
可达路径已实测：C2.3 刻意把 ±inf 留在 `raw_value`（转为 invalid flag 而非 NaN）→
某键观测全为非有限值 → 以 `NO_FINITE_VALUE` 进 quarantine → 聚合出 `"[Infinity]"`。
**代价落在最痛处**：quarantine 就是"不可发布观测"的审计轨迹，
而**恰好是描述源里最坏数据的那条记录无法被标准工具读取**。
同一次聚合还**丢掉了 reader 的 `invalid_reason`**，故发布行**无法区分
"源说了无穷"与"源什么都没说"**——而这个区分正是 C2.3 特意建立的。
**clean 批次全程不受影响**，纯属证据格式问题。

三个候选：字符串哨兵（`"Infinity"`）／ `null` 加标志位 ／ 把 `invalid_reason` 带下去。
**三者都会改变已持久化列的内容从而改变 `record_hash`**，且 migrations 已定义该列——
故需要决定，不宜代改。

**可达性收窄（2026-09-06 16:00，续二十二）**：上面"可达路径已实测"指的是**经公开 API 构造的帧**，
**不是源数据**。实测否证了后者：

- **DolphinDB 的 DOUBLE 列存不下 ±inf**——上传 `inf`/`-inf`/`1e309` 读回来**都是 NULL**，
  且所有算术通路（`1/0`、`log(0)`、`exp(1000)`、`pow(10.0,400)`、`1e308*10`）**也都返回 NULL**；
- 活的 `value` 列在 `factor_data1..11` 上**全是 DOUBLE**（C1.5 实测 typeString）；
- reader 对 `value` **不做任何算术**（只有 `pd.to_numeric`），
  对 `source_reader.py` / `materializer.py` / `deduplication.py` grep 算术运算符与会上溢的
  numpy 函数**零命中**。

**故 `raw_value` 在任何真实读取路径上都不可能是 ±inf**，`"[Infinity]"` 只能由进程内手工构造的帧产生。
**缺陷本身不打折**（列格式确实违反 RFC 8259、`invalid_reason` 确实被丢掉），
但**定级应从"正在污染审计轨迹"改为"潜在的 API 契约缺陷"**。

**再次收窄（2026-09-06 19:10，续三十）：这个缺陷所在的谱系根本不是冻结基线的谱系。**
`[Infinity]` 出自 `materializer.py` 聚合 quarantine 证据的路径，属 **(A) 治理/去重谱系**
（YesLab → `deduplicate_factor_observations` → `factor_observation_clean`），
**消费者是遗留链**；而**冻结集基线走 (B) 重放谱系**
（Tushare → 公式重放 → `factor_daily`），`materialize_frozen_factor_daily.py`
对 `deduplicate` / `factor_observation_clean` **零命中**，**完全不经过去重器与 materializer**。
**故本决定与冻结基线的关键路径无关**，其紧迫性只与"遗留链是否保留"（**裁决 3**）和
"(A) 谱系是否会被冻结集采用"（**决定 A 的 A2**）挂钩。
**权衡因此改变**：三个候选都要付"改 `record_hash`"的代价，
而收益侧不再是"源里最坏那条记录读不出来"，而是"API 使用者构造出 inf 时读不出来"。
**优先级请据此重估**（仍可独立随时定）。

## 3b. 决定 H（新增）：源水位一致性的不变量该放在哪一层

**问题**：C5.5 的六种故障里，「源水位中途变化」是**唯一在任何一层都不被检测**的一种。
实测证据（详见计划审计续二十一）：

- **`db/publish.py` 里 `source_watermark_id` 零命中**——发布器校验业务键、分区归属、DQ、
  版本与指针状态，**但不看 lineage**。一个行来自两个源快照的批次，发布路径与干净批次完全相同。
- **批内混合当前不可能**（每个 materializer 对整帧盖同一个水位），
  **故暴露面在批间**：同一对象的两个月、同一 `data_version`、一读在源变动前一读在后。
  **每批内部一致 ⇒ 任何按批的检查都看不见 ⇒ 该版本装着混源的行。**
- **`RunContext.build` 把水位折进 `data_version`**（`sorted(set(watermarks))`），
  故源变动**确实改变版本号**（要紧的一半：不会与干净 run 相撞）；
  但该集合**无键**，**不能回答"是同一张表中途动了，还是本来就读了几张表"**。
- **`verify_factor_daily_backfill.py` 核验的是版本字符串**（观测版本集合 == 预测版本），
  **不是**已发布行的水位列是否单值。

**后果**：源中途移动 → run 正常完成、正常发布、指针照常推进 →
**混源的行成为正式可见版本，且没有任何一层报错或记录哪张表动过。**

**三个候选位置：**

- **(H-i) `StagedBatch.validate` 加批内检查**：改动最小，**但抓不到真正的暴露面**——
  批内混合本就不可能发生，故它对所有现存批次静默通过、批间混合照旧。
  **它会制造"已经防住了"的错觉**，因此**不建议单独采用**。
- **(H-ii) 发布器跨批记住该版本已写过的水位**：能抓住，但需要发布器持有跨调用状态或回查已发布行，
  而 `V2BatchPublisher` 现在是无状态的（只靠注入的 pointer reader 感知外部）。
- **(H-iii) 发布后核验「一个 data_version × 一个对象 × 一张源表 ⇒ 一个水位」**：
  **能抓住且不改发布路径**，与 `verify_factor_daily_backfill.py` 已有的
  「单一 data_version」核验同类，**最贴合现有结构**；
  代价是**事后拦下而非事前阻止**（混源行会先落库，再由核验器拒绝推进指针）。

**倾向 (H-iii)**。**未实施**：(H-ii) 新增一条能让发布失败的拒绝路径，
(H-iii) 新增一个必须被编排器调用的核验步骤，**两者都改变运行链行为**，
而 Task 2.4 正在逐位复现。
**现状已用两条 characterization test 钉住**（`tests/unit/db/test_publish.py`），
其中一条经变异验证：**把 (H-i) 直接加上去会让它失败**，
故日后补这条不变量必然是一次显式的、有意识的改动，而不是静默生效。

## 3c. 决定 I（新增）：是否给 C 计划补一条"接线"验收标准

**问题**：C 计划的每一款都在问"实现了吗、测了吗"，**没有一款问"生产里有任何东西用它吗"**。
后果已实测：§1 的六个组件**每一个都能完全满足自己的条目文本**，而生产里零调用者；
生产真正用的冻结集是一份**人工裁决的 JSON**（`factor_set_frozen_v1.json`），
其身份**不是** `create_factor_set` 的内容寻址哈希。**决定 A 因此在 C8 才浮现，而它本应在 C1 就浮现。**

**评审建议的判据**（原文）："each governance module has at least one production caller,
or is explicitly marked design-reference"（每个治理模块至少有一个生产调用者，
或显式标注为设计参考）。

**选项**：

- **(I-i) 补进 C 计划的完成判据**：会让 §1 的六处**立刻从"已交付"变成"未满足"**，

  **代价最大、信息量也最大。**
- **(I-ii) 只作为一条独立的"接线状态"附录**：不改任何勾选，只把"谁调用谁"固化成文书，
  并要求**新增治理模块时同时登记调用者**。代价小，但**决定 A 仍会在下一轮同样晚地浮现**。
- **(I-iii) 不做**：接受"逐款核验 + grep 抽查"作为发现手段。

**不代做**：验收标准是计划的撰写权。**倾向 (I-i)**，理由是本清单里**已有两条决定（A、E）

**同类风险的一个具体实例（本轮已修，可作判据的样例）**：给规划器加了 `schema_errors` 参数

**"已修"与"已写"的差别就在这一行**，而没有任何既有条目会要求检查它。

## 3f. 决定 L（新增）：结构覆盖率的权威 scope 是哪一个，门 2 该读谁

**事实（只读实测，工件 `structural_coverage_scope_reconciliation.txt`）**：
`factor_quality_snapshot` 里**只存在两个** `STRUCTURAL_COVERAGE` scope——
`SCREEN_TRAIN2020_2024_STRUCTURAL_COVERAGE_V1` 与 `_V2`，

它只产出工件、不写快照。

**后果**：**任何读该表的消费者至今读的都是那份基于错误源的清单**——
门 2（`verify_admission_consistency`）、准入决策表、以及未来任何审计。
而那份清单**在两个方向上都不对**，且这不是新发现：
`screen_factor_daily_coverage.py` 的 docstring **早已写明**准入那次筛查跑在 **YesLab 源表**上、
而冻结链消费的是 **`factor_daily`**，该错配产生了
**一个假阴性**（`yeslab_375` **从未被结构筛查**，实测 43.9–62.8% 覆盖、低于 C6.2 的 0.70 门）
**和两个假阳性**（`yeslab_398`/`yeslab_464` 在**源表**上 1159 / 1185 天（共 1212），

预检自己也打了 NOTE：*"blocking status despite median coverage 0.9978 >= 0.7;
inspect the scope's other criteria"*——**续二十九就是那次 inspect。**

**另有三个冻结因子在快照里根本没有行**：**206、375、443_reg30_max20_v1**。
206 与 443 经活体筛查为 PASS，**而 375 是三套度量里最差的一个**。
即：**唯一从未被筛查、又确实有问题的因子，正是问题最重的那个**——
这不是巧合，而是"筛查跑在错误的源上"的直接后果。

**为什么"顺手把修正版发布进去"不能做**：
`verify_admission_consistency.py` 的 `BLOCKING_SCOPE_SUBSTRINGS = ("STRUCTURAL_COVERAGE",)`
是**子串匹配**，故新旧两份 scope 会**同时**被当作阻塞，
门 2 的清单会从 7 个变成 **8 个并集（含两个已知假阳性）**——**发布修正版反而让门 2 更错。**

**选项**：

- **(L-i) 发布修正 scope + 让门 2 只读指定 scope**：把子串匹配改成"权威 scope 名单"，
  并向 `dfs://QuantResearchV2Test` 写入一个新 scope（**additive、不动既有行**）。
  **最正确**：库里第一次有一份基于**被消费的表**的结构覆盖率。
  **代价**：一次 DB 写入（故与**决定 K** 相关：若 K 选独立库/前缀，L 的写入目标随之变）
  + 改一道治理门的匹配语义。
- **(L-ii) 不发布，改为在冻结契约 `conflicts` 数组里记录这六个**：
  这正是门 2 的字面要求（*"the contract's conflicts array must record this or the factors
  must be removed"*）。**但它会改动冻结契约**（含其 `data_version`），属 owner 行为，
  **且它就是裁决 4 (iii) 的机械后果**——**故 L-ii 与裁决 4 应一并定，不该分两次**。
- **(L-iii) waive 门 2**，理由写清（"快照基于错误的源、已由活体筛查取代，权威清单是这六个"）：
  **改动最小**，但**把一份已知有误的快照留在库里继续被别的消费者读到**，
  且 waive 是一次性动作、**不会修好数据**。

**倾向 (L-i) 先、(L-ii) 随后；(L-iii) 只作临时措施且必须写明过期条件。**
**不代做**：(L-i) 要写库并改一道治理门的匹配语义，(L-ii) 要改冻结契约，
(L-iii) 是放弃一道门——**三者都是 owner 的动作。**

**与裁决 4 的关系（要紧）**：**门 2 与门 3/4 不是同一个问题。**
门 3（`factor_coverage_screen`）与门 4（`fold_coverage`）读的是**活体 `factor_daily`**，
它们的失败是**真实的覆盖率不足**，即裁决 4 的标的；
门 2 的失败是**读错了工件**，即本决定的标的。
**把三者混为"覆盖率问题"会 waive 掉一道本该修的门、或修一道本该 waive 的门。**
