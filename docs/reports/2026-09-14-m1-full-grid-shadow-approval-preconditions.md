## 2. M0R 没有、M1 有的第一道前置：**先注册**

F6.1 要执行的是 `WALK_FORWARD_PASSED → SHADOW` 这个**状态转换**，
而它要求模型**已在册且状态为 `WALK_FORWARD_PASSED`**。**M1 现在不在册**（上表，机器读出）。
所以 M1 的路径比 M0R 多一步，顺序是固定的：

1. **注册**：`DRAFT → WALK_FORWARD_PASSED`，绑定证据哈希。
   **证据已齐备且已被独立验证**：`promotion_evidence.json` 能被 `load_walk_forward_evidence` 接受，
   registry 自己重算的 G1–G6 与报告逐位相同（链式看守第 3 阶段，09-13）。
2. 然后才谈得上 F6.1 的人工核验与 `→ SHADOW`。

**注册哪一份 M1 是所有者裁决项**：`m1_parallel_v1`（单配置载体，+0.005845，已被取代）
与 `m1_full_v1`（全 27 格，+0.007827，已归档判定）都过门，但代表不同的搜索规模与不同的谱系证据。
本文按**全网格版**写，因为它是归档判定、也是 M2 发射时 `--prior-report` 实际引用的那一份。
**注意注册不等于部署决定**：状态阶梯是
`DRAFT → WALK_FORWARD_PASSED → SHADOW → LOCKED_TEST_APPROVED → …`，
注册记的是"走查结果"这件事本身。

## 3. M1 特有的三条实质前置

### 3.1 【本轮新测出，对 M1/M2/M3 都成立】影子服务必须钉住 torch 线程数，否则分数会漂，而且**没有任何门会发现**

**事实链（每一环都核过）**：

1. **已训练的 torch bundle 的前向不是线程稳定的**（实测，非推论）：
   同一份 `m1_v2` F1 bundle（803,572 行）在 **1/2/4/8 线程下逐位相同**，
   在 **16 线程差 4.805844e-05、52 线程差 4.923683e-05**，且 16 与 52 彼此也不同；
   四档全 0 排除了"误差随线程数连续累积"的解释，而 5e-5 的量级是
   **近似并列股票之间的秩反转（会改变选股名次）**，不是末位舍入。
2. **复现审计之所以能报 0.0，是因为它把自己钉到该运行记录的线程数**
   （`recorded_run_threads()` 从**工作区的检查点 manifest** 读 `torch_intraop_threads`；
   混合多个值的工作区直接拒绝）。M1 因此钉到 1，日志明写
   `scoring under torch intra-op threads=1 (the run recorded 1; the host default was 52)`。
3. **而这个线程数不在已发布的 bundle 里**：`m1-f1/model_card.json` 只有四个字段
   （`dataset_id`、`family`、`model_code_version`、`model_status`），
   bundle 里是 `config.json` / `feature_order.json` / `preprocessing.json` / 三个 `seed-*.pt` /
   `signature.json` / `checksums.sha256` / `validation_predictions.parquet`——**没有任何一处记线程数**。
   也就是说：**离开那个工作区，重算出 0.0 所需的条件就丢了。**
4. **服务侧一行线程配置都没有**：`src/research_v2/inference/` 下只有 `reproduction.py`
   与线程有关（而且是**读**，不是设）；`torch_scoring.py` / `predictor.py` / `daily_pipeline.py`
   与 `configs/inference/daily.yaml`、`configs/production.yaml`、`configs/base.yaml`
   都**没有** `set_num_threads` / `configure_torch_threads` 之类调用（已逐文件核过）。

**推论（这是本文最重要的一条）**：把一个 torch 候选（M1，将来还有 M2/M3）放到影子里、
在默认 52 线程的宿主上打分，**得到的分数与被审计、被签名的那份不一致**，
差异量级足以改变近似并列股票的顺序；而**现有任何一道门都不会发现**——
PSI 比的是分布、监控比的是数据与分数健康，没有一道会把影子分数与 bundle 重算值逐行对比。

**处置分两层**：

* **立刻可做、不需要改代码（建议写进影子运行手册）**：
  **在影子/生产打分进程启动时把 torch intra-op 与 inter-op 都钉到 1**
  （即该运行记录的线程数），并在进程内**记录实际线程数**留痕。
  钉 1 线程的谱系本来就是"身份可移植、任意宿主可精确审计"的那一类
  （任何宿主都能把自己钉到 1），这也是当初把训练钉到 1 的理由。
* **正确的长期修法（本轮**未**合并，理由见下）**：把 `torch_intraop_threads` 写进 model card / bundle，
  让它**随工件旅行**，服务侧从工件读并自钉，而不是靠部署脚本记住。
  这需要改 card 的字段集（`torch_model_card()` 在驱动里）与服务侧加载路径，
  而**驱动在 M2/M3 在飞期间不能改**（spawn 每折从磁盘重新导入），
  且 M2 结束后链式看守会**立即**发射 M3，中间没有安全窗口。
  所以它属于与另两条驱动修复同一类的"改好了也要等合并窗口"的改动。

### 3.2 四折是四个不同架构，影子服务到底用哪一个 bundle，需要**写下来**

M0R 四折用的是**同一个钉死配置**，所以"用哪个 bundle"这个问题对它几乎不存在。
M1 全网格四折各自独立选出了**四个不同配置**
（`128/3/0.0`、`128/2/0.2`、`128/2/0.0`、`128/3/0.1`），
但它们共用**一个 model_id**（`sha256:5d01ec8f…`），
而 shadow pointer 指向的是 **model_id + model_version**（`registry/active_pointer.py`），
不是某个折的 bundle。

**因此批准前需要明确并记录**：某个打分日由**哪一个折的 bundle** 出分数
（按训练窗截止？按最新折？），这个规则目前**没有在工件或 F 计划里被明确写出**，
本文不代为设定。对 M1 这一条比对 M0R 要紧，因为四折的架构确实不同——
选错折不只是数值差异，而是**用了另一个模型**。

### 3.3 选择偏差：M1 的 +0.007827 含验证集选择的乐观成分，M0R 的 +0.009149 不含

同基线、同 945 日集，G4 可直接相减：**M0R 高 0.001322（约 17%）**。
但 M0R 的网格钉死为单配置（**无**验证集选择），M1 是从 **27 格**里按验证集 RankIC 挑的（**有**选择），
所以真实差距**大于** 0.001322。

**含义**：若目标是"影子期跑最强的那个"，证据支持 **M0R**；
若目标是"影子期跑一个符合'复杂候选'字面定义的 torch 模型"，则是 **M1**（且需先注册）。
**shadow pointer 只有一个**，所以先后顺序仍是所有者决定（M0R 前置清单 §4 已记同一件事）。
两者不必二选一：60 有效日是按"状态为 SHADOW 且 pointer 指向该模型"的成功日计的，
先后跑有明确语义，但**总时长会叠加**。
